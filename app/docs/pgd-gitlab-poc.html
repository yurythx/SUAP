POC — PGD × GitLab: lançamento automático de execuções

Cada MR vira uma execução (RIT) no PGD do SUAP — inferida da Entrega PES, confirmada pelo servidor. Guia passo a passo para a demonstração.

0 · Visão geral ▾

O que a demo prova: ao pedir o lançamento num MR, o assistente lê a issue+diff, descobre a qual categoria de trabalho (Entrega PES) aquilo pertence, estima as horas, mostra um resumo, o servidor confirma, e o SUAP grava 1 RIT por MR (idempotente). O servidor segue no controle: o RIT entra como rascunho (EM_CADASTRO_RIT) e é validado no envio mensal.

MR no GitLab→ skill /pgd-rit→ infere entrega (PES) + estima horas→ servidor confirma→ RIT no PGD

3 componentes (já implementados e testados):

CamadaO que fazOnde
Backend SUAPEndpoints ninja (entregas-disponiveis, lancar-rit, rit-do-mr) + serviço que cria o RIT; campos de proveniência no RITrepo suap
Tools MCPConectam o assistente ao SUAP (lista entregas, lança RIT, lê status), com auth OAuth2repo suap-mcp

Resposta à pergunta "basta criar o AplicacaoOAuth2?": No SUAP, o passo manual de autenticação é só esse (a app OAuth2 client-credentials). Além dele, o POC precisa de: o backend desta branch rodando com a migração aplicada, e dados de demonstração (um servidor com PIT do mês + entregas homologadas + o mapeamento GitLab). O resto — configurar o MCP, validar o token, rodar a skill — fazemos localmente. Os passos abaixo cobrem tudo isso.

1 · SUAP — criar a aplicação OAuth2 (autenticação) ▾

O MCP autentica no SUAP via OAuth2 client-credentials (machine-to-machine). Você cria uma AplicacaoOAuth2 confiável; ela gera client_id + client_secret.

1.1 Criar a app confiável SUAP

No host do SUAP, na venv do projeto: python manage.py shell e cole:

from api.models import AplicacaoOAuth2
from django.contrib.auth import get_user_model

User = get_user_model()
owner = User.objects.get(username='SEU_USUARIO_SERVICO')  # qualquer user ativo; vira o request.user

app = AplicacaoOAuth2(
    name='PGD GitLab Bot',
    client_type=AplicacaoOAuth2.CLIENT_CONFIDENTIAL,
    authorization_grant_type=AplicacaoOAuth2.GRANT_CLIENT_CREDENTIALS,
    skip_authorization=True,   # torna a app "trusted" (só admin pode)
    user=owner,                # OBRIGATÓRIO: TrustedAppAuth usa app.user como request.user
)
client_secret_plano = app.client_secret   # CAPTURE AGORA (é hasheado no save)
app.save()
print('client_id     =', app.client_id)
print('client_secret =', client_secret_plano)
Copie o client_secret imediatamente. O SUAP guarda só o hash; depois do save() ele não pode ser recuperado (só regenerado).

1.2 Validar o token (prova que a auth funciona) SUAP

Do seu terminal, troque a URL/credenciais e rode:

curl -s -X POST "https://SEU_SUAP/o/token/" \
  -d "grant_type=client_credentials&client_id=CLIENT_ID&client_secret=CLIENT_SECRET" | jq

Esperado: {"access_token":"…","expires_in":36000,"token_type":"Bearer",…}

Fala na apresentação: "Não guardamos token de longa duração nem senha — a app pega um token curto sob demanda; se vazar, revoga-se a app. É o padrão M2M que o próprio SUAP recomenda."

2 · SUAP — backend desta branch + dados de demonstração ▾

Caminho rápido (recomendado p/ a demo): depois de subir o backend (2.1), o seed command abaixo (2.2-rápido) cria de uma vez o cenário inteiro — servidor mapeado + PIT homologado + Entregas PES + (com a flag) a app OAuth2. Ele substitui os passos 1.1 e 2.2 e já imprime o trecho do contexts.yaml. Um teste de aceitação garante que o cenário é lançável de verdade (o gate completo do PGD passa).

2.1 Subir o backend com a migração aplicada SUAP

Na branch spec/pgd-execucao-gitlab (que tem os endpoints + a migração pgd2/0027 dos campos GitLab no RIT):

git checkout spec/pgd-execucao-gitlab
uv sync --all-groups
python manage.py migrate pgd2          # aplica a 0027 (campos gitlab_* no RIT)
python manage.py runserver             # ou o ambiente onde o MCP vai bater

A API fica em /api/pgd2/execucao-gitlab/….

2.2-rápido · Seed do cenário (faz 1.1 + 2.2 de uma vez) SUAP

Cria servidor mapeado + adesão + PIT homologado (EM_CADASTRO_RIT) + Entregas PES (Atendimento de erros, Desenvolvimento, Revisão de código) e, com --with-oauth-app, a app OAuth2 — imprimindo client_id/client_secret + o trecho do contexts.yaml:

python manage.py seed_pgd2_gitlab_demo \
  --username-gitlab USERNAME_GITLAB \
  --matricula MATRICULA_DO_SERVIDOR \
  --with-oauth-app

Idempotente: pode rodar de novo. Se já fez o 1.1 na mão, omita --with-oauth-app. Se usar este passo, pule o 2.2 manual abaixo.

2.2 Garantir os dados de demonstração (alternativa manual) SUAP

O fluxo só tem o que mostrar se existir, para um servidor: um PIT do mês homologado (em EM_CADASTRO_RIT) com pelo menos uma entrega homologada ligada a uma Entrega PES (com descrição/critérios), e o mapeamento do usuário → username GitLab.

# manage.py shell — mapear o servidor ao username do GitLab (autor do MR):
from demandas.models import AnalistaDesenvolvedor
from rh.models import Servidor
serv = Servidor.objects.get(matricula='MATRICULA_DO_SERVIDOR')
AnalistaDesenvolvedor.objects.get_or_create(
    usuario=serv.get_user(), defaults={'username_gitlab': 'USERNAME_GITLAB', 'ativo': True}
)
Use um servidor que já tenha o PIT do mês com entregas homologadas (o caso real). Se precisar de um cenário limpo e reproduzível para a demo, peça que eu gere um management command de seed.

2.3 Provar o backend ponta a ponta (token + dados) SUAP

Com o access_token do passo 1.2, liste as entregas candidatas:

TOKEN="COLE_O_ACCESS_TOKEN"
curl -s "https://SEU_SUAP/api/pgd2/execucao-gitlab/entregas-disponiveis/?gitlab_username=USERNAME_GITLAB" \
  -H "Authorization: Bearer $TOKEN" | jq

Esperado: {"entregas":[{…,"pes_descricao":"…","pes_criterios_avaliacao":"…","metrica":…}]}. Se vier 404, o username não está mapeado (passo 2.2). Se vier lista vazia, falta PIT/entrega homologada do mês.

Fala: "Essa chamada já mostra o coração da inferência: as categorias do PIT vêm com a descrição e os critérios da Entrega PES — é contra isso que o assistente casa a issue."

3 · Local — configurar o MCP (este computador) ▾

3.1 Apontar o contexto SUAP LOCAL

Em ~/.config/coding-agents/contexts.yaml, na seção do contexto (ex.: ifrn), inclua a seção suap com o client_id (não é segredo):

contexts:
  ifrn:
    suap:
      base_url: "https://SEU_SUAP"
      client_id: "CLIENT_ID_DO_PASSO_1.1"
      token_keychain: "coding-agents/suap/ifrn"
    gitlab:
      base_url: "https://gitlab.ifrn.edu.br"
      token_keychain: "coding-agents/gitlab/ifrn"

3.2 Guardar o client_secret LOCAL

O token_keychain agora guarda o client_secret. Via variável de ambiente (nome derivado do keychain em MAIÚSCULAS, /→_):

export CODING_AGENTS_SUAP_IFRN="CLIENT_SECRET_DO_PASSO_1.1"

Ou no macOS Keychain: security add-generic-password -a "$USER" -s "coding-agents/suap/ifrn" -w "CLIENT_SECRET"

3.3 Recarregar o MCP no Claude Code LOCAL

O servidor suap-mcp já está no .mcp.json. Reinicie o Claude Code para carregar as tools novas (get_entregas_disponiveis_pgd2, lancar_rit_execucao_gitlab, get_rit_do_mr_pgd2). A skill /pgd-rit aparece na lista de skills.

Garanta que o suap-mcp está na branch feat/pgd2-lancar-rit (auth client-credentials + tools pgd2).

4 · A demonstração — lançar o RIT a partir de um MR ▾

Tenha um MR de teste no GitLab cujo autor seja o servidor mapeado no 2.2 (idealmente ligado a uma issue de bug/feature).

4.1 Rodar a skill DEMO

No Claude Code, aponte o MR e rode:

/pgd-rit  (no MR https://gitlab.ifrn.edu.br/.../-/merge_requests/NN)

4.2 Acompanhar a inferência DEMO

Mostre o assistente: lendo o diff/issue → listando as categorias (Entrega PES) → escolhendo a que casa (bug → Atendimento de erros/chamados; feature → Desenvolvimento) → estimando as horas pelo diff → montando título + link da issue.

Fala: "Ele não duplica o trabalho no SUAP: o RIT leva um resumo + o link do GitLab. A fonte continua sendo o GitLab."

4.3 Dry-run e confirmação DEMO

O resumo aparece (entrega, horas, descrição). A skill faz um dry-run (não grava) e só grava depois que você confirma. Confirme.

Fala: "O servidor está sempre no controle — nada é gravado sem a confirmação explícita."

4.4 Verificar o RIT no PGD DEMO

Abra o PGD do servidor: o RIT aparece na entrega, em EM_CADASTRO_RIT, com quantidade = 1 e o link do MR na descrição. As horas somam no total da categoria.

4.5 Mostrar a idempotência DEMO

Rode /pgd-rit de novo no mesmo MR → ele atualiza o mesmo RIT (não duplica). Chave: (projeto, MR).

5 · Bordas (opcional na demo) ▾

5.1 Comentário no merge DEMO

Ao mergear o MR, o job de CI pgd-rit-merge (push na master) resolve o MR do commit e comenta no MR qual RIT foi lançado. (requer validação no GitLab real)

5.2 Limpeza de órfão SUAP

Se o MR for fechado sem merge, o cron descartar_rits_gitlab_orfaos (agendado no pgd2/beat.py) remove o RIT. Para demonstrar na hora:

python manage.py descartar_rits_gitlab_orfaos --dry-run   # lista o que removeria
python manage.py descartar_rits_gitlab_orfaos             # remove os órfãos

6 · Pontos de fala / Q&A ▾

Pergunta provávelResposta curta
"E se a issue não casar com nenhuma categoria?"A skill avisa e não grava — o servidor lança manual ou pede a entrega ao gestor.
"Não vai poluir o PGD?"1 RIT por MR, só título + link (não duplica conteúdo). O total da categoria é a soma — comportamento nativo do PGD.
"Quem garante que é o servidor certo?"O servidor é resolvido pelo username_gitlab e validado contra a entrega (IDOR coberto) + o gate nativo pode_cadastrar_entrega_rit.
"E a segurança do token?"OAuth2 client-credentials: segredo revogável, token curto em cache, sem senha de usuário, sem token de longa duração solto.
"Mexeu no fluxo manual atual?"Não. Reusa a mesma regra do cadastro manual de RIT; o lançamento automático é só mais um caminho de entrada.
"E se o servidor já enviou o RIT do mês?"O gate nega (período fechado) → a skill avisa e orienta lançamento manual.
